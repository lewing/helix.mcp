## Durable Patterns and Learnings

- Prefer service/decorator boundaries for cache and offline behavior; mock `IHelixApiClient` / AzDO client interfaces rather than transport internals.
- Normalize optional parameters at semantic boundary and reuse same algorithm for URL construction, cache keys, validation.
- Strict-mode compatibility lives in `CallToolFilter` aliases before parameter binding; remove alias keys after promotion so unknown-param checks stay meaningful.
- Startup/background maintenance must retain completion handle, pin construction-time cutoffs, dispose in cancel → bounded join → fault observation → pool cleanup order.
- Windows file replacement needs right primitive: `File.Replace` for existing artifacts, `File.Move` for absent artifacts. Don't rely on exception-driven retry.
- Eval/snapshot tests should prove no live network fallback by using offline clients that throw and asserting exact snapshot-derived plans.

## Learnings (Summary)

**Queue-monitor evidence plan:** Timeline issues sufficient for `azdo evidence plan` to represent failed Helix work items without Helix API calls; keep parsed monitor jobs out of artifact `entries[]`, but fail closed with `incompleteDetails[].code` when monitor rows unparseable/unresolved/paged/truncated.

**Acquisition error classification:** Must classify at provider boundary and serialize with explicit converter; MCP SDK default JSON options can ignore enum converter attributes in `structuredContent`, so use acquisition-owned JSON options for error envelopes. Eval/offline cache misses now `provider=cache` acquisition errors, not `InvalidOperationException`. Valid HTTP-200 empty logs remain successful even when requested logId surprising.

**Lockout protocol:** When lead rejects commit and locks out author, different agent must revise. AzDO empty-log ambiguity: empty body + absent logId = `not_found`; empty body + logId present = success. Validate in `AzdoService.GetBuildLogAsync` (service layer), not `AzdoApiClient` (provider layer), not cached until proven.

**Acquisition error defense-in-depth:** Sanitize URL query/fragment values in `AcquisitionErrorFactory` and again in `HlxAcquisitionException` so manually constructed test/MCP errors cannot leak SAS tokens. CLI-wide acquisition handling belongs in `ConsoleAppFramework` global filter; direct unit tests instantiating command classes bypass filter and must exercise generated CLI/filter pipeline or shared writer explicitly.

**Snapshot replay and negative cache:** `not_in_snapshot` only for true misses; deterministic live provider failures are negative cache rows keyed exactly like positive evidence, replay with original provider/kind + `source=snapshot`, `replayed=true`, `recordedAt`. Public live validation must avoid Azure CLI auth-scoped AzDO cache keys (or provide same env token in eval). PR 1 paging/cache keeps MCP capped, CLI `--all` writes complete versioned keys (`changes:v2`, `testruns:v3`, etc.) that eval-mode capped calls probe first and slice in memory. SQLite metadata must encode NUL bytes; otherwise full-log rows round-trip as empty and capped offline log tails miss/corrupt.

**Collector final details:** Capture final AzDO auth state after live fetches (not before), because `CachingAzdoApiClient` updates `CacheOptions.AuthTokenHash` lazily on first authenticated call. Optional Helix file downloads never evict required evidence: clamp budget to `min(--max-total-bytes, cacheCap - requiredBytes)`, not raw policy. Post-write verification bypass TTL for presence checks (`GetMetadataIgnoringTtlAsync`). Default manifest path resolve next to effective cache root, not CWD. SQLite TEXT binding silently truncates at embedded NULs; all NUL-bearing/marker-prefixed values must encode before binding.

### 2026-10-02/03 — P0-1 timeline triage implementation

Implemented Dallas's P0-1 design (bounded triage timeline views) plus the shared P0 contracts it needs: `AzdoTimelineProjector` (new pure Core projector), unified `TimelineProjectionResult` (single `records`/JSON array regardless of projection — triage/compact rows or raw `AzdoTimelineRecord`), `IEvidenceDeliveryStore`/`FileEvidenceDeliveryStore` (delivery dir outside snapshots; eval mode roots it at OS temp, not the snapshot dir), new `hlx_read_evidence` MCP tool, and `McpPresentationBudget` (byte-shrink loop + evidence-materialization fallback for MCP).

**Key pitfalls found by Lambert's contract tests (`TimelineViewContractTests`, `TimelineProjectorContractTests`, `EvidenceDeliveryContractTests`, `TimelineViewReplayTests` — all written in parallel, read-only, never edited):**
- `McpJsonUtilities.DefaultOptions.DefaultIgnoreCondition == WhenWritingNull` globally omits null properties; fields a caller's `GetProperty` always expects (pagination `next`, `EvidenceReadResult.Next`) need `[JsonIgnore(Condition = JsonIgnoreCondition.Never)]` explicitly, or `KeyNotFoundException` on the client side.
- The SDK's default JSON encoder escapes `"` as `\u0022` (6 bytes) not `\"` (2 bytes) when a JSON string is embedded inside another JSON string (the `content[].text` duplicate of `structuredContent`) — real, unavoidable, and a major multiplier on tight byte budgets. Budgeting must tolerate moderate overage for a single necessarily non-empty row rather than ever returning a zero-row page (design: "never a self-repeating zero-row page").
- `TimelineProjectionResult.ViewId` must hash actual timeline *content* (not just `Id`+`Records.Count`) or a changed live build (retried attempt, new issue) silently reuses a stale viewId.
- A shrink/fallback loop that mutates request fields (e.g. `PreviewChars`/`PreviewIssueLimit`) on the *returned* response, without baking the same mutated values into its own continuation args, breaks the stale-viewId check on the next hop — keep the "accepted" candidate's own fields consistent with what a fresh default call would recompute.
- "Complete" for a list page is `offset==0 && allSelectedReturned`, independent of whether `next` is null — a final nonzero page at `offset>0` is still `truncated=true` with a whole-selection recovery action, not `complete=true`.
- The `result → resultFilter` global MCP argument alias (prior `azdo_search_timeline`-only hack) must be scoped per-tool-name once a second tool (`azdo_timeline`) declares its own canonical `result` parameter, or the alias clobbers it.
- Phase-row seed/count exclusion (triage/summary default `includePhase=false`) must happen *before* seed matching, not only at display time, or `matched`/`counts.byTypeResult` double-count suppressed Phase rows.

Live validation: default MCP triage for build 1621192 (14 matched/25 selected, 1524 raw records) returned 2 rows / 10,020 wire bytes with the monitor work-item failure (`System.Diagnostics.Process.Tests`) visible in the first preview; build 1600801 (11 matched/15 selected) returned 5 rows / 12,109 bytes with the 3 failed DeviceTests tasks first. Both within the 12,288-byte default budget. Forced a 1500-byte budget on an explicit single full record to prove live evidence materialization + `hlx_read_evidence` round-trip. `hlx collect azdo-build 1621192 --export` + `HLX_EVAL_SNAPSHOT=... env -i` offline replay reproduced byte-identical `viewId` and full/triage/compact/summary shapes with no network.

268/269 new contract tests pass; one known deviation (`ripley-timeline-deviations.md`): an explicit 27,000-char-name selector under an aggressive 4,096-byte budget materializes a zero-row delivery receipt at ~4,351 bytes (~6% over target) because the documented `EvidenceDescriptor` contract (`sourceFingerprint`/`backingCacheKey`/`capturedAt`/`freshness`) costs more than the remaining headroom at that floor; kept the documented fields rather than trimming the descriptor contract to force this one edge case under budget.
